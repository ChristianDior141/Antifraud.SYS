# Incident Response & Personal-Data Breach Notification

**Стандарты:** GDPR Art.33/34 • ISO/IEC 27001 A.16 • NIST SP 800-61 • **Версия:** 1.0 • **Дата:** 2026-06-04

> Процедура реагирования на инциденты информационной безопасности и уведомления
> об утечке персональных данных. Привязана к встроенному модулю управления
> инцидентами Antifraud.SYS.

## 1. Классификация серьёзности

| Уровень | Критерий | Пример |
|---|---|---|
| Critical | Утечка/компрометация PII, потеря доступности ключевого сервиса | Дамп БД, RCE, кража учётных данных админа |
| High | Попытка компрометации, эскалация привилегий | Брутфорс с обходом lockout, подозрительный массовый доступ к PII |
| Medium | Аномалия без подтверждённого ущерба | Всплеск 401/403, единичный аномальный доступ |
| Low | Событие для наблюдения | Единичные неуспешные входы |

## 2. Жизненный цикл реагирования (NIST 800-61)

1. **Detect (обнаружение).** Источники: `audit_logs` (события `USER_LOGIN_FAILED`, `ACCOUNT_LOCKED`, `LOGIN_BLOCKED_LOCKED`, `PII_VIEWED`, `MFA_FAILED`), проверка целостности аудита (`/privacy/audit/integrity`), мониторинг/алерты, обращения.
2. **Triage (оценка).** Назначить серьёзность, зафиксировать инцидент-тикет, определить затронутые данные/субъектов.
3. **Contain (сдерживание).** Отозвать токены (`/auth/logout` / denylist), заблокировать/деактивировать учётные записи, при необходимости включить `processing_restricted`, изолировать компонент.
4. **Eradicate (устранение).** Устранить первопричину (патч, ротация секретов `SECRET_KEY`/`ENCRYPTION_KEY`, смена паролей).
5. **Recover (восстановление).** Вернуть сервис, проверить целостность данных и аудита, усилить мониторинг.
6. **Lessons learned.** Постмортем, обновление правил/контролей, запись в реестр.

## 3. Уведомление об утечке персональных данных (GDPR)

### 3.1 Уведомление надзорного органа (Art.33)
- **Срок:** без неоправданной задержки и **не позднее 72 часов** с момента, когда стало известно об утечке.
- **Условие:** если утечка вероятно создаёт риск для прав и свобод субъектов.
- **Содержание:** характер утечки, категории и примерное число субъектов/записей, контакты DPO, вероятные последствия, принятые/планируемые меры.

### 3.2 Уведомление субъектов данных (Art.34)
- **Когда:** если утечка вероятно создаёт **высокий** риск для субъектов.
- **Как:** прямое сообщение, понятным языком, с описанием мер и рекомендаций.
- **Исключения:** данные были зашифрованы/непонятны (например, PII в системе шифруется at-rest), либо приняты меры, устраняющие высокий риск, либо это потребует несоразмерных усилий (тогда — публичное уведомление).

### 3.3 Внутренний реестр утечек (Art.33(5))
Все утечки (даже не подлежащие уведомлению) фиксируются: факты, последствия, принятые меры.

## 4. Роли и ответственность

| Роль | Ответственность |
|---|---|
| Дежурный/обнаруживший | Зафиксировать инцидент, оповестить координатора |
| Incident Coordinator | Управление реагированием, эскалация |
| DPO | Оценка необходимости уведомления, коммуникация с регулятором/субъектами |
| Администратор/ИБ | Технические меры сдерживания и устранения |
| Руководство | Решения, внешние коммуникации |

## 5. Контрольный список (первые 72 часа)

- [ ] Зафиксировать время обнаружения и факты
- [ ] Присвоить серьёзность, создать тикет
- [ ] Определить, затронуты ли персональные данные и чьи
- [ ] Сдержать: отозвать токены/сессии, заблокировать аккаунты, ротация секретов
- [ ] Проверить целостность аудита (hash-chain)
- [ ] Оценить риск для субъектов (DPO)
- [ ] При риске — уведомить надзорный орган ≤72ч (Art.33)
- [ ] При высоком риске — уведомить субъектов (Art.34)
- [ ] Запись во внутренний реестр утечек
- [ ] Постмортем и обновление контролей

## 6. Связь с продуктом
Технические события и кейсы ведутся в модуле инцидентов и журнале аудита
Antifraud.SYS. Для security-событий предлагается отдельная таблица
`security_events` и SIEM-интеграция (см. `docs/SECURITY_COMPLIANCE_AUDIT.md`, §9 — план развития).
